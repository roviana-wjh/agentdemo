## 1. 引言：Redis 为何成为后端开发的“瑞士军刀”

如果说关系型数据库是互联网世界的“账本”，负责严谨地记录每一笔交易，那么 Redis 就是那个站在账本背后，用闪电般的速度递上数据的“超级助手”。在动辄百万级并发、毫秒级响应的应用场景下，数据库磁盘的 I/O 瓶颈早已成为过去式，而内存计算则是突破这一瓶颈的关键。

**Redis（Remote Dictionary Server）**，这个诞生于 2009 年的开源项目，最初由意大利开发者 Salvatore Sanfilippo（网名 antirez）开发，旨在解决其实时日志分析系统的高性能需求。它从一个简单的内存键值存储，历经十余年的迭代，如今已成长为一个集数据结构服务器、分布式缓存、消息队列、搜索引擎、流处理引擎于一体的全能型基础设施。它不仅是一把“瑞士军刀”，更是现代高并发架构中不可或缺的数据枢纽。

---

### 1.1 从 Memcached 到 Redis：不仅仅是“快”

回顾缓存技术的发展，Memcached 曾经是分布式缓存的事实标准。但 Redis 的出现，彻底改变了游戏规则。Memcached 只能存储简单的字符串，而 Redis 则提供了丰富的数据结构。这种差异并非简单的功能堆砌，而是思维模式的转变。

让我们通过一个简单的对比来看清 Redis 的核心优势：

| 特性维度 | Memcached | Redis |
| :--- | :--- | :--- |
| **数据结构** | 仅支持 String | String、Hash、List、Set、ZSet、Bitmaps、HyperLogLog、Geo、Stream |
| **持久化** | 不支持（重启即失） | 支持 RDB 快照与 AOF 日志，可数据恢复 |
| **原子操作** | 仅支持简单的 `incr/decr` | 原生支持 Lua 脚本，复杂事务与原子性保证 |
| **高可用** | 客户端分片 | 主从复制 + 哨兵模式 + Cluster 集群 |
| **功能扩展** | 无 | 发布订阅、Lua 脚本、模块化（RedisJSON、RediSearch） |

**场景示例**：假设我们要实现一个“最近 1 小时内最热门的 10 个商品”排行榜。

- **传统方案**：使用关系型数据库查询 `ORDER BY score DESC LIMIT 10`，随着数据量增长，全表扫描和索引维护成本极高。
- **Redis 方案**：使用 **ZSet（有序集合）**。仅需一行代码即可完成更新，查询也只需一次 O(log N) 操作，内存级的计算速度比磁盘快几个数量级。

```python
# Python 伪代码示例
import redis

r = redis.Redis(host='localhost', port=6379, db=0)

# 模拟用户点击商品，点击率 +1
def record_click(product_id, score=1):
    # 假设以当天日期为 key，0 为分数，product_id 为成员
    r.zincrby("hot_products:2023:10:27", score, product_id)

# 获取 Top 10 商品
def get_top_10():
    # 按分数降序排列，取前 10 个
    return r.zrevrange("hot_products:2023:10:27", 0, 9, withscores=True)
```

这段代码在 MySQL 中可能需要精心设计索引和优化 SQL，而在 Redis 中，它就是一把直插数据心脏的利刃。

### 1.2 核心优势：不仅仅是缓存，更是数据结构服务器

很多人误以为 Redis 只能做缓存，这是对其最大的误解。Redis 的价值在于它是**基于内存的数据结构服务器**。它允许你在内存中构建复杂的业务模型，而无需频繁地序列化和反序列化对象。

#### 1. 性能与单线程模型

Redis 的极致性能（通常可达 10 万+ QPS）不仅源于内存，更源于其**单线程事件循环**架构。这意味着它不需要处理并发锁竞争的问题，避免了上下文切换的开销。虽然单线程，但得益于 IO 多路复用（如 epoll），它能够高效处理海量并发连接。在 6.0 版本后，虽然引入了多线程 I/O，但核心的命令执行逻辑依然保持单线程，保证了原子性。

#### 2. 持久化与可靠性

它并非易失性存储的“短命鬼”。Redis 提供两种持久化机制：

- **RDB（Redis Database）**：在指定时间间隔内生成数据集的时间点快照，适合灾难恢复。
- **AOF（Append Only File）**：记录每一次写命令，重启时回放。通过 `fsync` 策略可以在数据安全与性能之间取得平衡。

#### 3. 原子性与 Lua 脚本

原子操作是避免竞态条件的金钥匙。在分布式场景下，多个客户端同时修改一个键极易出错。Redis 提供的 `WATCH`、`MULTI` 事务，以及强大的 Lua 脚本支持，让你可以将多条命令打包，服务器保证其原子执行。

---

### 1.3 分布式架构中的“定海神针”

在微服务和云原生架构盛行的今天，Redis 的角色更加多元化。它不仅是保护数据库的“防洪墙”（缓存），更是微服务间通信的“高速公路”。

一个典型的电商系统架构中，Redis 的身影无处不在：

1. **会话管理（Session Storage）**：用户登录状态存储在 Redis 中，多个应用服务器无状态化，易于水平扩展。
2. **购物车（Hash）**：使用 Redis Hash 存储，方便维护商品 ID 与数量。
3. **库存扣减（Lua + String）**：通过 Lua 脚本保证库存不被超卖。
4. **分布式锁（Setnx）**：解决多个服务实例之间的资源争抢问题。
5. **异步队列（List 或 Stream）**：将耗时的邮件/短信发送任务放入消息队列。
6. **排行榜与计数（ZSet & Incr）**：如前述的电商大屏可视化、文章点赞数。

这种架构下，Redis 充当了粘合剂和数据中枢，使得系统可以轻松应对“双十一”等流量洪峰。

## 2. 基础架构与核心数据结构

### 2.1 单线程事件循环：为什么 Redis 能如此之快

当我们谈论 Redis 的高性能时，最常被提及的设计决策就是**单线程模型**。乍看之下，单线程似乎应该成为性能瓶颈，但 Redis 却能在单线程下轻松达到每秒十万甚至百万级的 QPS（查询每秒）。这背后的关键在于：Redis 巧妙地绕开了多线程编程中棘手的锁竞争、上下文切换和 CPU 缓存失效问题，同时将所有操作建立在**内存访问**和**非阻塞 I/O** 的基础之上。

Redis 的事件循环基于 `aeEventLoop`（位于 `ae.c` 文件）实现，它本质上是一个基于多路复用（`epoll`、`kqueue` 或 `select`）的 Reactor 模式。事件源主要分为三类：

1. **文件事件（File Event）**：即客户端的连接、读写事件
2. **时间事件（Time Event）**：如过期键清理、AOF 持久化等定时任务
3. **信号事件**：处理 `SIGTERM` 等信号

简化模型如下：

```
while (1) {
    // 找出最近需要执行的时间事件
    aeSearchNearestTimer();

    // 阻塞等待文件事件，但最久等待 nearestTimer 的时间
    numevents = aeProcessEvents(eventLoop, AE_FILE_EVENTS | AE_DONT_WAIT);

    // 处理所有已就绪的文件事件
    for (j = 0; j < numevents; j++) {
        // 按顺序执行读事件 -> 写事件
        processFileEvent(fe);
    }

    // 处理到期的时间事件
    processTimeEvents();
}
```

**为什么单线程反而更快？**

以 `GET` 命令为例，整个过程不涉及磁盘 I/O、不加锁、不进行上下文切换，每一个操作都在微秒级别完成。如果引入多线程，即便有锁，线程间的切换开销（约 2~5 微秒）加上缓存失效的代价，往往已经超过命令本身的执行时间。

但需要澄清一个重要趋势：**Redis 6.0+ 引入了多线程 I/O，但核心命令执行仍是单线程。** 多线程仅用于网络读写。原因是：网络数据包的解析和序列化通常是 CPU 密集型工作，单线程在这一部分存在瓶颈，但执行命令的核心逻辑（如修改数据结构）保持单线程，从而避免了锁竞争。

Redis 7.0 进一步引入了多线程的主动过期（Active Expiry），以及基于 `command_t` 的细粒度优化。

### 2.2 内存模型：内存分配器与对象管理

Redis 中每个键值对都被封装为一个 `redisObject`（在 `server.h` 中定义）：

```c
typedef struct redisObject {
    unsigned type:4;       // 类型：string, list, hash, set, zset
    unsigned encoding:4;   // 编码：int, embstr, raw, hashtable, quicklist, skiplist...
    unsigned lru:LRU_BITS; // 用于内存淘汰的 LRU / LFU 时间
    int refcount;          // 引用计数，用于共享对象与内存回收
    void *ptr;             // 指向底层数据结构的指针
} robj;
```

这个设计相当精妙。同一类型的数据，可以有不同的**内部编码（encoding）**，Redis 会根据实际情况选择最优的数据结构。

例如，对于一个 `SET` 类型的键，如果存储的全部是整数且数量小于 `set-max-intset-entries`（默认 512），则会使用 `INTSET` 编码（有序整数数组，内存极为紧凑）；一旦超出限制或者插入非整数元素，则升级为 `HT`（哈希表）编码。

内存分配方面，Redis 使用内存分配器（默认是 `jemalloc`）而非系统原生 `malloc`。`jemalloc` 的优势在于：

- 减少内存碎片
- 支持 `malloc_stats_print` 等方式查看统计
- 对多线程分配有优化

此外，Redis 支持**共享对象**技术：小于 `OBJ_SHARED_INTEGERS`（默认 10000）的整数键值，会被全局共享，而不是为每个键创建不同的对象。这显著降低了小整数的内存开销。

**内存淘汰策略预览**：当设置了 `maxmemory`，Redis 会根据 `maxmemory-policy`（如 `allkeys-lru`、`volatile-ttl` 等）进行键淘汰。每种策略均基于 `redisObject` 中的 LRU 或 LFU 信息做出决策。

### 2.3 五种基础数据类型

#### 2.3.1 String（字符串）

**底层编码**（三种）：

| 编码       | 条件                                        | 存储形态                         |
| ---------- | ------------------------------------------- | -------------------------------- |
| `INT`      | 值可被解析为 64 位长整型                    | 直接存储整数，无 `ptr` 指向额外对象 |
| `EMBSTR`   | 字符串长度 ≤ 44 字节（Redis 3.2+）          | `redisObject` 与 `sdshdr` 连续分配内存 |
| `RAW`      | 字符串长度 > 44 字节                        | 分两次分配，`ptr` 指向独立的 `sdshdr` |

`EMBSTR` 只需要一次内存分配，且在读取时能更好利用 CPU 缓存。44 这个数字很有讲究：因为 `redisObject`（16 字节）+ `sdshdr`（至少 8 字节）+ 结束符，刚好凑满 64 字节的高速缓存行。

**适用场景：**

- 计数器（`INCR`、`DECR`）
- 缓存对象（以 JSON 序列化后存储）
- 分布式锁（`SETNX` + `EXPIRE`）

**示例：**

```bash
> SET user:1000 '{"name": "Alice", "age": 30}' EX 3600
OK
> INCR page:visits
(integer) 1
> GET page:visits
"1"
```

#### 2.3.2 List（列表）

**底层编码演替：**

- Redis 3.2 之前：`ziplist`（压缩列表）→ 转换阈值后变为 `linkedlist`（双向链表）
- Redis 3.2 之后：**`quicklist`** 成为唯一编码。quicklist 是一个由多个 `ziplist` 组成的双向链表

每个节点（`quicklistNode`）内部都是一个 `ziplist`，节点大小受 `list-max-ziplist-size` 控制（默认 -2，表示每个节点最大 8 KB）。采用这种混合结构的原因是：单纯的链表每个节点需要维护两个指针（8 字节），内存浪费大且缓存局部性差；而纯 `ziplist` 在数据量大时的插入删除效率低（需要移动内存）。

**适用场景：**

- 消息队列（配合 `BRPOPLPUSH` 实现可靠队列）
- 时间线 / 最近文章列表（`LPUSH` + `LTRIM`）

**示例：**

```bash
> LPUSH notifications:user1 "order_shipped" "payment_received"
(integer) 2
> LRANGE notifications:user1 0 -1
1) "payment_received"
2) "order_shipped"
```

#### 2.3.3 Hash（哈希）

**底层编码：**

- `ziplist`（紧凑存储）：当键值对总数 < 512（`hash-max-ziplist-entries`）且每个键值对长度 < 64 字节时
- `hashtable`（字典）：超出阈值后转换

`hash-max-ziplist-entries` 和 `hash-max-ziplist-value` 参数可调。使用 `ziplist` 时，键值对在内存中是连续存储的：`[field1, value1, field2, value2, ...]`，查找需要遍历，但因为数据量小，性能可接受。

**适用场景：**

- 缓存对象字段（而不是整个 JSON 序列化字符串）
- 存储用户属性、购物车数据

**示例：**

```bash
> HSET user:2000 username "bob" email "bob@example.com" age 25
(integer) 3
> HGETALL user:2000
1) "username"
2) "bob"
3) "email"
4) "bob@example.com"
```

**选用 Hash 而非 String 存放对象：**

- String 需要整体序列化/反序列化；Hash 支持单独操作字段
- 对于长期存在的热对象，Hash 可以做到按需加载字段

#### 2.3.4 Set（集合）

**底层编码：**

- `INTSET`：全部元素为整数且集合大小 ≤ 512
- `HASHTABLE`：其他情况

`INTSET` 使用有序数组存储，支持二分查找，内存利用率高，特别适合存储整数 ID。

**适用场景：**

- 去重（如每日 UV 记录 `SADD`）
- 集合运算（交集、并集、差集）查找共同好友
- 标签系统

**示例：**

```bash
> SADD tags:article:1 "redis" "database" "performance"
(integer) 3
> SADD tags:article:2 "redis" "cache"
(integer) 2
> SINTER tags:article:1 tags:article:2
1) "redis"
```

#### 2.3.5 ZSet（有序集合）

**底层编码：**

- `ziplist`：元素数量 < 128（`zset-max-ziplist-entries`）且每个 member 长度 < 64 字节
- `skiplist + dict`：超出后转换

**跳表（skiplist）实现**：

Redis 的 ZSet 采用了一个**跳跃表（skiplist）+ 哈希表（dict）**的混合结构：

- `dict` 维护 `member → score` 的映射，用于 O(1) 的按成员取分数
- `skiplist` 维护按分数排序的有序链，支持 O(log N) 的范围查询和插入删除

为什么不用平衡树（红黑树）？这是出于几个考虑：

1. 跳表实现更简单，不易出错
2. 跳表在范围查找（`ZRANGEBYSCORE`）时性能优于平衡树，因为不需要进行复杂的旋转维护
3. 跳表的层数随机生成，配合概率保证期望复杂度 O(log N)，实际上对 Redis 的负载特征足够高效

跳表节点结构示意：

```c
typedef struct zskiplistNode {
    sds ele;                 // 成员
    double score;            // 分数
    struct zskiplistNode *backward;
    struct zskiplistLevel {
        struct zskiplistNode *forward;
        unsigned long span;  // 跨越的节点数（用于排名计算）
    } level[];
} zskiplistNode;
```

**适用场景：**

- 排行榜（如实时热榜）
- 延迟队列（score 用于表示到期时间）
- 固定时间窗口统计

**示例：**

```bash
> ZADD leaderboard 1000 "player_a" 950 "player_b" 875 "player_c"
(integer) 3
> ZREVRANGE leaderboard 0 2 WITHSCORES
1) "player_a"
2) "1000"
3) "player_b"
4) "950"
```

### 2.4 三种高级类型

#### 2.4.1 Bitmap（位图）

Bitmap 本质上是 String 类型的一种特殊用法，通过操作字符串的二进制位来实现。它没有独立的数据结构，而是将字符串视为一个位数组。

**常用命令**：`SETBIT`、`GETBIT`、`BITCOUNT`、`BITOP`。

**底层原理**：一个包含 N 个字符的字符串，可提供 8N 个位。位按 0 开始索引。

**适用场景：**

- 用户签到（每天一个位，记录 N 天）
- 在线状态（用户 ID 映射到位索引）
- 月度活跃用户统计（`BITCOUNT` 即可统计人数）

**示例：**

```bash
# 用户 ID 101 在 2024-01-01 签到（偏移量 = 用户ID）
> SETBIT sign:2024-01 101 1
(integer) 0
> SETBIT sign:2024-01 102 1
(integer) 0
> BITCOUNT sign:2024-01
(integer) 2    # 当天共有 2 人签到
```

Bitmap 的核心优势在于**极致的内存效率**。存储一个 10 亿用户的在线状态，只需 10 亿位 ≈ 125 MB；如果使用 Set 存储在线用户 ID，每个 ID 至少 4 字节，10 亿用户将需要 4 GB。

#### 2.4.2 HyperLogLog

用于估计基数（去重后的数量），标准误差 0.81% 的概率性算法。

**底层原理**：HLL 使用回归的哈希函数，通过观测哈希值中的前导零个数来估计基数。内部使用 2^14 = 16384 个寄存器，每个寄存器 6 bit，总内存占用固定约 12 KB（无论处理多少数据）。

**适用场景：**

- 统计 UV（独立访问用户）
- 统计每天访问过的 IP 数
- 大型集合的基数估计（精确度要求不高时）

**示例：**

```bash
> PFADD daily_unique_users user1 user2 user3
(integer) 1
> PFADD daily_unique_users user4 user5
(integer) 1
> PFCOUNT daily_unique_users
(integer) 5
```

**需要注意**：HLL 去重基于概率，无法逐条判断某个成员是否存在（不像 Set 的 `SISMEMBER`）。它只擅长「总量统计」，不适合「包含检查」。

#### 2.4.3 GEO（地理位置）

Redis 3.2+ 引入的地理位置支持，底层使用 **ZSet** 实现（其 member 为地理位置名称，score 为将经纬度编码后的 52 位整数）。

**底层原理**：GEO 使用 **Geohash** 编码算法。将地球视为二维平面，经度范围 [-180, 180]，纬度范围 [-85.05112878, 85.05112878]（Web Mercator 投影限制）。然后使用二进制对经纬度进行交替区间二分（奇数位放经度，偶数位放纬度），将二维坐标转换为一维整数。最后加上一个固定的偏移，使得 score 始终为正数（便于在 ZSet 中存储）。

**核心命令**：

- `GEOADD`：添加位置
- `GEODIST`：计算两点距离
- `GEORADIUS`：查询指定半径内的位置

**适用场景：**

- 附近的人 / 附近的商家
- 基于位置的推送服务

**示例：**

```bash
> GEOADD restaurants 116.397 39.908 "restaurant_a"   # 北京天安门附近
> GEOADD restaurants 116.410 39.921 "restaurant_b"   # 故宫附近
> GEODIST restaurants restaurant_a restaurant_b km
"2.1945"        # 距离 2.19 公里
> GEORADIUS restaurants 116.397 39.908 5 km WITHCOORD
1) 1) "restaurant_a"
   2) 1) "116.39700156450271606"
      2) "39.9080018997194394"
2) 1) "restaurant_b"
   2) 1) "116.41000145673751831"
      2) "39.9210004806518555"
```

### 2.5 各类型总结与选型建议

| 类型 | 底层结构 | 插入/查找复杂度 | 典型内存占用 | 最佳场景 |
|------|---------|----------------|------------|---------|
| String | SDS / int | O(1) | 较低（简单值） | 缓存、计数器、分布式锁 |
| List | quicklist | 头部/尾插 O(1)，随机索引 O(N) | 中 | 消息队列、时间线 |
| Hash | ziplist / dict | O(1) | 中等 | 对象缓存、字段修改 |
| Set | intset / dict | O(1) | 较低（整数时） | 去重、集合运算 |
| ZSet | ziplist / skiplist+dict | O(log N) | 较高（两个结构） | 排行榜、排序队列 |
| Bitmap | 位数组 | O(1) | 极低 | 布尔状态统计 |
| HyperLogLog | 寄存器数组 | O(1) | 固定 12KB | 大基数去重估算 |
| GEO | ZSet（geohash 编码） | O(log N) | 同 ZSet | 附近位置搜索 |

**选型指导原则：**

1. **纯缓存场景**：String 优先，考虑使用 JSON 序列化
2. **需要单独修改对象的多个字段**：Hash（比整存整取 String 更高效）
3. **按时间排序且不断增长**：List（左侧写入 + 右侧读取或 `LTRIM`）
4. **需要做交集/并集运算**：Set
5. **需要按分数排序且动态更新**：ZSet
6. **百万级以下布尔统计**：Bitmap；**千万级以上基数估算**：HyperLogLog
7. **位置服务**：GEO

## 3. 持久化与高可用机制

### 3.1 持久化：内存数据的“保险丝”

Redis 作为一款基于内存的键值数据库，其最大的性能优势恰恰也是它最大的隐患——数据完全驻留在内存中，一旦进程崩溃或宿主机断电，所有数据将瞬间归零。持久化机制就是为了给这份“易失”的内存数据加上一根保险丝。

#### 3.1.1 RDB：时间点快照

RDB（Redis Database）机制的工作原理可以用一句话概括：**在指定的时间间隔内，将内存中的数据集以二进制格式写入磁盘**，生成一个经过压缩的 `.rdb` 快照文件。

**触发方式**分为手动与自动两种。手动通过 `SAVE` 或 `BGSAVE` 命令触发。`SAVE` 是同步操作，会阻塞 Redis 主进程，生产环境几乎不使用；`BGSAVE` 则通过 fork 子进程完成快照写入，主进程继续服务。自动触发则通过配置文件中的 `save` 指令实现：

```conf
# 900秒内至少有1个key发生变化，则触发BGSAVE
save 900 1
# 300秒内至少有10个key发生变化，则触发BGSAVE
save 300 10
# 60秒内至少有10000个key发生变化，则触发BGSAVE
save 60 10000
```

**底层原理**涉及 Linux 的写时复制（Copy-On-Write, COW）技术。当 `BGSAVE` 执行时，主进程 fork 出一个子进程。此时父子进程共享同一份物理内存。子进程负责将数据写入临时 RDB 文件，而主进程继续处理写命令。当主进程需要修改某个内存页时，操作系统会先复制该页，确保子进程仍能看到 fork 时刻的数据版本，从而保证了快照的一致性。

**RDB 的优势**非常明显：

- **文件紧凑**，适合做冷备和跨机房传输。
- **恢复速度极快**，加载 RDB 文件启动 Redis 通常只需秒级。
- **性能影响小**，主进程 fork 子进程后几乎无 I/O 开销。

**但它的短板也同样致命**：**它无法做到实时持久化**。因为 `BGSAVE` 是重量级操作，fork 子进程在内存量大时可能阻塞主进程数百毫秒，因此不能太频繁执行。若在两次快照之间发生宕机，这段时间的写入数据将全部丢失。此外，fork 操作在内存中会短暂出现双倍内存占用，对内存规划需谨慎。

#### 3.1.2 AOF：追加式命令日志

AOF（Append Only File）机制的理念与 RDB 截然不同：**它并不保存数据快照，而是记录每一条修改数据的写命令**。当 Redis 重启时，通过回放 AOF 文件中的所有命令来重建数据。

**工作流程**分为三步：命令追加（append）、文件写入（write）、文件同步（sync）。

每当执行一条写命令（如 `SET`、`LPUSH`），Redis 会将该命令以 Redis 协议格式追加到 `server.aof_buf` 缓冲区中。那么缓冲区何时真正落盘呢？这由 `appendfsync` 配置决定，提供了三种策略：

| 配置值 | 行为 | 安全性 | 性能 |
|--------|------|--------|------|
| `always` | 每条写命令都调用 `fsync()` 同步到磁盘 | 最安全，最多丢失1条数据 | 最慢 |
| `everysec` | 每秒调用一次 `fsync()` | 最多丢失1秒数据（默认） | 快 |
| `no` | 由操作系统决定何时刷盘（通常30秒左右） | 可能丢失大量数据 | 最快 |

生产环境默认使用 `everysec`，它在性能与安全性之间取得了最佳平衡。

**AOF 的重写机制**是必须理解的要点。随着运行时间增长，AOF 文件会无限膨胀。例如对同一个 key 执行了 1000 次 `SET`，AOF 中会记录 1000 条命令，但最终只有最后一条有意义。`BGREWRITEAOF` 命令会遍历内存中的当前数据，生成一条最小的命令集合来恢复当前状态，替换掉冗余的历史日志。

新版本 Redis 7.0 引入了 **AOF 多部分文件** 设计，将 AOF 拆分为基础文件（RDB 格式）与增量文件（AOF 格式），重写时临时文件与旧文件独立管理，极大地优化了重写时的磁盘占用与清理逻辑。

**AOF 的优缺点**：优势是数据安全性高（最多丢失 1 秒数据），日志可读性好，便于误操作后的修复。缺点是 AOF 文件通常比 RDB 文件大得多，恢复速度也相对较慢。

#### 3.1.3 混合持久化：鱼与熊掌兼得

既然 RDB 恢复快但丢数据多，AOF 数据安全但恢复慢，那么是否可以将两者结合？

Redis 4.0 引入了 **混合持久化** 方案，默认开启（`aof-use-rdb-preamble yes`）。在 AOF 重写时，不再是纯粹写命令日志，而是将重写时刻的内存快照以 RDB 格式写入 AOF 文件的开头，再将重写期间的增量命令以 AOF 格式追加在文件尾部。这样组合的文件同时具备 RDB 快速加载的优点和 AOF 数据安全性高的优点，重启时只需加载 RDB 部分，再回放少量尾部日志即可完成恢复。

**生产实践建议**如下：

- 若你的场景允许丢失分钟级数据（如缓存），且追求极致的启动速度——仅开启 RDB 即可。
- 若数据不可丢失（如业务订单状态、计数），务必开启 AOF，设置 `appendfsync everysec`。
- 最稳妥的做法是 **两者同时开启**。Redis 重启时会优先加载 AOF 文件（因为更安全），RDB 文件则作为日常冷备。同时开启后的 `BGSAVE` 和 `BGREWRITEAOF` 会触发写时复制，需要注意内存余量要预留至少一倍。

### 3.2 主从复制：数据冗余的分发

持久化解决了“进程重启后的生存问题”，但无法应对“单点物理故障”，例如硬盘损坏、服务器宕机。主从复制（Replication）通过将主节点（Master）的数据分发到多个从节点（Replica），实现了数据的热备份与读写分离。

#### 3.2.1 复制的原理剖析

从节点的首次复制采用**全量同步**，后续则基于**增量同步**维持一致性。以 Redis 5.0+ 为例，复制流程如下：

1. **建立连接**：从节点执行 `REPLICAOF <master_ip> <port>`（旧版命令为 `SLAVEOF`），向主节点发送 `PSYNC` 命令，携带主节点运行 ID 与复制偏移量。
2. **全量重同步**：若主从节点是首次连接或断连太久导致主节点的复制积压缓冲区已无对应偏移量，则触发全量同步。主节点执行 `BGSAVE` 生成 RDB 快照，同时将新写入的命令缓存到复制积压缓冲区。RDB 快照传输给从节点后，从节点清空自身旧数据，加载 RDB；随后学习缓冲区中的增量命令。
3. **增量同步**：全量同步完成后，主节点会将后续每条写命令实时发送给从节点。从节点通过偏移量控制同步进度。

这里有一个**关键细节**：从节点不仅接收主节点的推送，还会持续向主节点发送 `REPLCONF ACK {offset}`，上报自己的复制偏移量。主节点据此判断从节点是否延迟，并可通过 `INFO replication` 查看 `lag` 字段了解延迟情况。

#### 3.2.2 无磁盘复制与复制拓扑模式

在主节点执行 `BGSAVE` 期间，如果磁盘性能成为瓶颈，可以开启 `repl-diskless-sync yes`，主节点将 RDB 数据直接通过 socket 流式传输给从节点，避免写盘带来的 I/O 压力。

拓扑上，除了标准的一主多从，还可以搭建**树形级联结构**：例如主节点 A → 从节点 B，而从节点 B 同时作为下层的“主节点”挂载从节点 C。这种模式降低了主节点的发送压力，但需注意 B 节点宕机会导致 C 节点无法同步最新数据，因此更推荐多主多从加哨兵的架构。

#### 3.2.3 复制的缺陷与解决

主从复制存在一个先天性缺陷：**它无法自动故障转移**。当主节点宕机时，从节点持有的是旧数据（可能滞后几百毫秒或秒级），需要人为介入提升某个从节点为新的主节点。重启的应用进程需要修改写流量的指向。为解决这个痛点，哨兵（Sentinel）模式应运而生。

---

### 3.3 哨兵模式：高可用的守护者

#### 3.3.1 哨兵的职责

Redis Sentinel 是一个独立运行的分布式监控系统，通常以 **三台以上节点** 部署（奇数个）。它的核心职责有四点：

1. **监控**：持续检查主节点与从节点是否处于可达状态。
2. **通知**：当被监控的 Redis 实例发生故障时，哨兵通过 API 通知管理员或其他应用程序。
3. **自动故障转移**：当主节点发生
